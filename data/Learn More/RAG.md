# RAG (Retrieval-Augmented Generation) — المرجع الشامل

مرجع متكامل من الصفر حتى المفاهيم المتقدمة، مع ربط مباشر بمشروعك (IFC Compliance Checker).

---

## الفصل 1: المشكلة الأساسية التي يحلها RAG

### 1.1 لماذا لا يكفي الاعتماد على LLM وحده؟
النماذج اللغوية الكبيرة (LLMs) مثل GPT أو Claude تُدرَّب على بيانات ضخمة لكن:
- **معرفتها محدودة بتاريخ معين** (Knowledge Cutoff) — لا تعرف أي معلومة جديدة بعد تاريخ التدريب.
- **لا تعرف بياناتك الخاصة** — مثل وثيقة الشروط الهندسية بمشروعك، أو ملفات شركتك الداخلية.
- **قد "تختلق" معلومات (Hallucination)** — تعطيك إجابة تبدو واثقة لكنها غير صحيحة، خصوصًا لو سألتها عن تفاصيل دقيقة غير موجودة أصلاً بذاكرتها.
- **تكلفة إعادة التدريب** على بيانات جديدة باهظة جدًا وغير عملية لكل تحديث بسيط.

### 1.2 الحل: RAG
بدل ما "تُعلّم" النموذج معلومات جديدة عبر إعادة تدريبه، تعطيه هذه المعلومات **مباشرة داخل الطلب (Prompt)** وقت الحاجة، بعد ما تكون "استرجعتها" (Retrieved) من مصدر بيانات خارجي.

**المعادلة ببساطة:**
```
RAG = Retrieval (استرجاع المعلومة الصحيحة) + Generation (توليد إجابة بناءً عليها)
```

### 1.3 مثال مبسّط
بدل أن تسأل النموذج: "ما هو الحد الأدنى لمساحة النافذة؟" وتعتمد على معرفته العامة (التي قد تكون خاطئة أو غير موجودة أصلاً)...
النظام يبحث أولاً داخل وثيقة الشروط الخاصة بك، يجد الفقرة ذات العلاقة، ثم يعطيها للنموذج ويقول له: "بناءً على هذا النص فقط، أجب عن السؤال".

## الفصل 2: المكونات الأساسية لأي نظام RAG

```
[وثائق المصدر] → [Chunking] → [Embedding] → [Vector Store]
                                                    ↓
[سؤال المستخدم] → [Embedding] → [Similarity Search] → [أفضل النتائج]
                                                    ↓
                              [Prompt يحتوي: السؤال + النتائج المسترجَعة]
                                                    ↓
                                              [LLM] → [الإجابة]
```

### 2.1 Chunking (تقطيع الوثائق)
لا يمكن إعطاء LLM وثيقة كاملة ضخمة كل مرة (تكلفة، حدود سياق، دقة أقل). لذلك نُقسّم الوثيقة إلى قطع صغيرة (Chunks) قابلة للاسترجاع بشكل مستقل.

### 2.2 Embeddings (التمثيل الرقمي الدلالي)
كل قطعة نص تُحوَّل إلى **متجه رقمي (Vector)** يمثل معناها الدلالي، وليس فقط كلماتها الحرفية. جملتان بمعنى متشابه لكن كلمات مختلفة تمامًا سينتج عنهما متجهات "قريبة" رياضيًا.

### 2.3 Vector Store (قاعدة بيانات المتجهات)
مكان تخزين كل هذه المتجهات، مصمم خصيصًا للبحث السريع عن "أقرب المتجهات" لمتجه سؤال معين (Similarity Search)، وليس بحث نصي تقليدي.

### 2.4 Retriever (المسترجِع)
الجزء المسؤول عن أخذ سؤال المستخدم، تحويله لمتجه، والبحث في الـ Vector Store عن أقرب N نتائج.

### 2.5 Generator (النموذج اللغوي)
يأخذ السؤال الأصلي + النتائج المسترجَعة، ويولّد إجابة نهائية مبنية عليها فقط (Grounded Generation).

## الفصل 3: Chunking بالتفصيل

### 3.1 لماذا حجم القطعة (Chunk Size) مهم جدًا؟
- **قطعة كبيرة جدًا**: تحتوي معلومات كثيرة غير ذات علاقة، مما يُضعف دقة البحث الدلالي (Embedding يمثل "متوسط" معنى مشوش).
- **قطعة صغيرة جدًا**: قد تفقد السياق اللازم لفهم الجملة (مثال: شرط هندسي مقسوم على قطعتين منفصلتين).

### 3.2 استراتيجيات التقطيع الشائعة

| الاستراتيجية | الوصف | متى تُستخدم |
|---|---|---|
| **Fixed-size chunking** | تقسيم بعدد ثابت من الأحرف/الكلمات | بيانات غير منظمة، بداية سريعة |
| **Sentence-based** | تقسيم حسب حدود الجمل | نصوص عامة، مقالات |
| **Paragraph-based** | تقسيم حسب الفقرات | وثائق منظمة (زي وثيقة شروطك بالتاسك) |
| **Recursive chunking** | يحاول التقسيم حسب فقرات، فإذا كانت طويلة يقسم لجمل، وهكذا تدريجيًا | الأكثر شيوعًا عمليًا (مستخدم بمكتبة LangChain) |
| **Semantic chunking** | تقسيم بناءً على تغيّر المعنى الدلالي فعليًا، مو مجرد علامات ترقيم | دقة أعلى، تكلفة حسابية أكبر |
| **Document-structure-aware** | يحترم عناوين Markdown، الجداول، القوائم | وثائق تقنية منظمة (الأنسب لمشروعك تحديدًا) |

### 3.3 Overlap (التداخل بين القطع)
غالبًا نترك تداخل بسيط بين القطع المتتالية (مثلاً 10-20%) حتى لا تُقطع معلومة مهمة بالضبط عند حدود قطعتين.

### 3.4 توصية عملية لمشروعك
بما إن وثيقة الشروط عندك صغيرة جدًا (3 شروط فقط)، الأفضل أن **كل شرط = قطعة واحدة مستقلة**، بدل تقطيع تلقائي عشوائي. هذا يضمن استرجاعًا دقيقًا 100% دون الحاجة لتعقيد إضافي.

## الفصل 4: Embeddings بالتفصيل

### 4.1 كيف تعمل رياضيًا (ببساطة)؟
النموذج المُدرَّب (Embedding Model) يحوّل أي نص إلى متجه (Vector) من عشرات أو مئات الأبعاد (مثلاً 384 أو 1536 بعدًا). النصوص متشابهة المعنى تقع "قريبة" من بعضها بهذا الفضاء الرياضي.

### 4.2 قياس التشابه (Similarity Metrics)
- **Cosine Similarity**: الأكثر استخدامًا، يقيس زاوية بين متجهين (القيمة من -1 إلى 1).
- **Euclidean Distance**: المسافة الإقليدية المباشرة بين نقطتين.
- **Dot Product**: أسرع حسابيًا، مستخدم أحيانًا في أنظمة كبيرة.

### 4.3 خيارات نماذج Embedding

| النموذج | محلي/API | ملاحظات |
|---|---|---|
| `sentence-transformers` (مثل `all-MiniLM-L6-v2`) | محلي، مجاني | خفيف وسريع، ممتاز للمشاريع الصغيرة والتاسكات |
| `text-embedding-3-small/large` (OpenAI) | API | جودة عالية، يحتاج API key وتكلفة |
| `Voyage AI embeddings` | API | تستخدمها Anthropic كتوصية مع Claude |
| `BGE` / `E5` models | محلي، مجاني | أداء منافس جدًا للنماذج المدفوعة، Open Source |

### 4.4 نقطة مهمة بمشروعك
بما إن التاسك يمنع استخدام API keys بالمستودع، **الخيار الآمن هو `sentence-transformers` محليًا** — لا يحتاج اتصال إنترنت وقت التشغيل ولا مفاتيح API.

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer('all-MiniLM-L6-v2')
embedding = model.encode("Minimum room area must be at least 12 m²")
# embedding الآن متجه رقمي (numpy array) بطول 384
```

## الفصل 5: Vector Stores بالتفصيل

### 5.1 لماذا لا نستخدم قاعدة بيانات عادية (SQL)؟
قواعد البيانات التقليدية ممتازة بالبحث الدقيق (`WHERE name = 'X'`)، لكنها غير مصممة أصلاً للبحث عن "أقرب متجهات" بفضاء متعدد الأبعاد بكفاءة — هذا يتطلب خوارزميات وبنى بيانات متخصصة (زي HNSW، IVF).

### 5.2 مقارنة أشهر الخيارات

| الأداة | النوع | متى تُستخدم |
|---|---|---|
| **FAISS** (من Meta) | مكتبة محلية، ليست قاعدة بيانات كاملة | سريعة جدًا، ممتازة للمشاريع الصغيرة/المتوسطة، لا تحتاج سيرفر منفصل |
| **Chroma** | قاعدة بيانات متجهات كاملة، محلية أو خادم | سهلة الاستخدام جدًا، مناسبة تمامًا لتاسك متوسط الحجم |
| **In-memory (يدوي)** | قاموس بايثون بسيط + numpy | لعدد قطع صغير جدًا (كحالتك بالضبط: 3 شروط فقط) |
| **Pinecone / Weaviate / Qdrant** | خدمات سحابية/إنتاجية | مشاريع إنتاجية كبيرة بملايين القطع |

### 5.3 توصية عملية لمشروعك
بما إن عندك 3 شروط فقط، **حتى FAISS تُعتبر "مبالغة" تقنيًا**. لكن بما إن التاسك يطلب صراحة "بناء RAG pipeline"، الأفضل استخدام **Chroma** أو **FAISS بسيط** لإظهار الفهم التقني الصحيح، حتى لو حجم البيانات الفعلي صغير.

```python
import chromadb

client = chromadb.Client()
collection = client.create_collection("building_conditions")

collection.add(
    documents=["Room area must be at least 12 m²", "..."],
    ids=["condition_1", "condition_2", "condition_3"]
)

results = collection.query(query_texts=["what is minimum window area?"], n_results=1)
```

## الفصل 6: عملية الاسترجاع (Retrieval) بالتفصيل

### 6.1 Dense Retrieval (الاسترجاع الدلالي)
هو ما شرحناه سابقًا: تحويل كل شيء لمتجهات ومقارنتها دلاليًا. ممتاز لفهم "المعنى" حتى لو الكلمات مختلفة.

### 6.2 Sparse Retrieval (الاسترجاع التقليدي)
مثل **BM25** أو **TF-IDF** — يعتمد على تطابق الكلمات الحرفية ووزنها الإحصائي، وليس المعنى. أسرع وأبسط لكن يفشل لو صيغة السؤال مختلفة تمامًا عن صيغة النص الأصلي.

### 6.3 Hybrid Retrieval (النهج الهجين)
يجمع بين Dense و Sparse معًا (بوزن معين لكل واحد)، للاستفادة من دقة المعنى ودقة التطابق الحرفي معًا. يُستخدم كثيرًا بالأنظمة الإنتاجية الحقيقية لأنه أكثر موثوقية من الاعتماد على طريقة واحدة فقط.

### 6.4 Top-K Retrieval
عدد النتائج المسترجَعة (K) — قيمة صغيرة جدًا قد تفوّت معلومة مهمة، وقيمة كبيرة جدًا "تُغرق" النموذج بمعلومات غير ذات علاقة (Noise) وتزيد التكلفة.

### 6.5 Re-ranking (إعادة الترتيب) — تقنية متقدمة
بعد الاسترجاع الأولي (مثلاً Top-20)، نستخدم نموذج ثانٍ أدق وأبطأ (Cross-Encoder) لإعادة ترتيب هذه النتائج فقط واختيار الأفضل منها (مثلاً Top-3). هذا يحسّن الدقة كثيرًا مقارنة بالاعتماد على الاسترجاع الأولي فقط.

```
سؤال → Retrieval سريع (يرجع 20 نتيجة تقريبية)
     → Re-ranker دقيق وأبطأ (يرتبهم من جديد)
     → أفضل 3 نتائج فعليًا تُرسل للـ LLM
```

## الفصل 7: مرحلة التوليد (Generation)

### 7.1 بناء الـ Prompt الصحيح (Prompt Grounding)
الجزء الأهم: يجب أن يُعطى النموذج تعليمات واضحة بأن يعتمد **فقط** على النص المسترجَع، وليس معرفته العامة.

مثال بنية Prompt نموذجية:
```
أنت مساعد يجيب فقط بناءً على السياق المُعطى أدناه.
إذا لم تجد الإجابة بالسياق، قل "لا توجد معلومة كافية" ولا تخترع إجابة.

السياق:
{النصوص المسترجَعة}

السؤال: {سؤال المستخدم}
```

### 7.2 تقليل الهلوسة (Hallucination) في مرحلة التوليد
- التأكيد الصريح بالـ Prompt على عدم الاختلاق.
- خفض قيمة **Temperature** (كلما قلّت، كانت الإجابات أكثر التزامًا بالنص وأقل "إبداعًا").
- إضافة اقتباس مباشر (Citation) من المصدر ضمن الإجابة، مما يجبر النموذج ضمنيًا على الالتزام بالنص الفعلي.

### 7.3 ملاحظة حرجة تخص تاسكك بالتحديد
بما إن التاسك يمنع صراحة اعتماد القرار النهائي (PASS/FAIL) على LLM، دور الـ Generation بمشروعك يجب أن يقتصر على:
- **تحديد** الشرط المناسب من الوثيقة (تصنيف/استرجاع).
- **شرح** الشرط بلغة مبسطة إن احتجت بالتقرير النهائي.

بينما **الحساب الفعلي والمقارنة الرقمية تبقى بكود بايثون حتمي بالكامل**، بدون أي تدخل من الـ LLM على الإطلاق.

## الفصل 8: أنماط معمارية لأنظمة RAG (من البسيط للمتقدم)

### 8.1 Naive RAG (النمط الأساسي)
الترتيب البسيط: Chunk → Embed → Retrieve → Generate. مناسب تمامًا لحالات بسيطة زي تاسكك.

### 8.2 Advanced RAG
يضيف تحسينات فوق النمط الأساسي:
- **Query Rewriting/Expansion**: إعادة صياغة سؤال المستخدم أو توسيعه لعدة صيغ قبل البحث، لزيادة احتمال إيجاد التطابق الصحيح.
- **HyDE (Hypothetical Document Embeddings)**: بدل تحويل السؤال مباشرة لمتجه، نطلب من LLM أولاً "تخيّل" إجابة افتراضية للسؤال، ثم نحوّل هذه الإجابة الافتراضية لمتجه ونبحث بها — أحيانًا تعطي نتائج أدق من السؤال الخام.
- **Re-ranking** (شرحناها بالفصل 6).

### 8.3 Modular RAG
تصميم مرن يسمح بتبديل أي مكوّن (Retriever، Vector Store، Re-ranker) بشكل مستقل حسب الحاجة، بدل نظام "متجمّد" بخط واحد ثابت.

### 8.4 Agentic RAG (متقدم جدًا)
بدل استرجاع واحد ثابت، يُعطى النموذج قدرة "اتخاذ قرار" بنفسه: هل يحتاج استرجاع إضافي؟ من أي مصدر؟ هل السؤال يحتاج تقسيمه لعدة أسئلة فرعية أولاً (Multi-hop reasoning)؟ يُستخدم في الأنظمة المعقدة (زي نظام YANA اللي حكينا عنه سابقًا، حيث الأسئلة قد تحتاج ربط معلومات من مصادر متعددة: BIM + كود بناء + تقرير تعارضات).

### 8.5 GraphRAG (متقدم جدًا)
بدل تخزين القطع كمتجهات مستقلة فقط، تُبنى **شبكة علاقات (Knowledge Graph)** بين المفاهيم، فيصير الاسترجاع قادر على تتبّع علاقات معقدة (مثال: "أي جدار يؤثر على أي غرفة يؤثر على أي كود بناء؟") — وهذا قريب جدًا من طبيعة بيانات BIM نفسها (عناصر مترابطة بعلاقات، تمامًا زي IFC).

> ملاحظة مهمة لمشروعك مستقبلاً: نظام BIMLens/YANA-BIM هو مرشح ممتاز لـ GraphRAG لاحقًا، لأن بيانات IFC أصلاً مبنية كعلاقات (Graph-like) وليست نصوصًا مسطحة.

## الفصل 9: تقييم أنظمة RAG (Evaluation)

### 9.1 لماذا التقييم صعب أكثر من الأنظمة التقليدية؟
لأن فيه مرحلتين منفصلتين ممكن يفشل أي منهما: الاسترجاع (جبت المعلومة الصح؟) والتوليد (فهمتها وعبّرت عنها صح؟).

### 9.2 مقاييس تقييم الاسترجاع
- **Precision@K**: من ضمن K نتيجة مسترجَعة، كم منها فعلاً ذو علاقة؟
- **Recall@K**: من ضمن كل النتائج ذات العلاقة الموجودة أصلاً، كم منها ظهر ضمن أفضل K؟
- **MRR (Mean Reciprocal Rank)**: هل النتيجة الصحيحة ظهرت بمرتبة متقدمة أم متأخرة؟

### 9.3 مقاييس تقييم التوليد
- **Faithfulness**: هل الإجابة مبنية فعلاً على النص المسترجَع، أم فيها اختلاق؟
- **Answer Relevance**: هل الإجابة تجاوب فعلاً على سؤال المستخدم؟
- **Context Precision/Recall**: مدى جودة السياق المُعطى للنموذج بالأساس.

### 9.4 أدوات تقييم جاهزة
- **RAGAS**: مكتبة بايثون مخصصة بالكامل لتقييم أنظمة RAG آليًا.
- **TruLens**، **DeepEval**: بدائل مشابهة.

### 9.5 توصية عملية لمشروعك
بما إن عندك 3 شروط فقط بوثيقة صغيرة جدًا، **اختبار يدوي بسيط كافٍ تمامًا** (تتأكد أن كل سؤال يرجع الشرط الصحيح المطابق له)، ولا داعي لتعقيد بأدوات تقييم إنتاجية ضخمة.

## الفصل 10: اعتبارات إنتاجية (Production Considerations) — للاطلاع فقط

هذه مو مطلوبة بتاسكك الحالي، لكن مفيدة تعرفها كخلفية لمستقبل مشروع BIMLens الأكبر:

- **Caching**: تخزين نتائج أسئلة متكررة لتقليل التكلفة والزمن.
- **Chunking ديناميكي**: تحديث القطع تلقائيًا عند تغيّر الوثيقة المصدر (Building Codes تتحدّث مثلاً).
- **Multi-tenancy**: فصل بيانات كل مشروع/عميل عن الآخر بنفس النظام.
- **Latency Budget**: كل مرحلة (Embedding → Retrieval → Re-ranking → Generation) تضيف زمن استجابة، يجب موازنته حسب حاجة التطبيق.
- **Monitoring**: تتبع جودة الإجابات بمرور الوقت (خصوصًا لو تغيّرت الوثائق المصدر).

## الفصل 11: تطبيق كامل ومبسّط على مشروعك

### 11.1 البنية المقترحة (الأنسب لحجم تاسكك)
```
knowledge_base.md         # الشروط الثلاثة، كل شرط بقسم منفصل
    ↓ (Document-structure-aware chunking — قسم = قطعة)
embeddings.py              # sentence-transformers محليًا
    ↓
in-memory vector store     # قاموس بسيط: {condition_id: (vector, text)}
    ↓
retriever.py                # Cosine similarity بسيط، Top-1 أو Top-3
    ↓
(اختياري) LLM يشرح الشرط المسترجَع بلغة مبسطة بالتقرير النهائي
    ↓
validators.py               # الحساب والمقارنة الفعلية — بايثون حتمي بالكامل، بدون LLM إطلاقًا
```

### 11.2 كود مبسّط يوضح الفكرة الكاملة end-to-end
```python
from sentence_transformers import SentenceTransformer
from sklearn.metrics.pairwise import cosine_similarity
import numpy as np

model = SentenceTransformer('all-MiniLM-L6-v2')

conditions = {
    "room_area": "The room's internal floor area must be at least 12 square meters.",
    "window_area": "The window area must be at least 10 percent of the room's internal floor area.",
    "sill_height": "The window sill height must be between 0.80 and 1.10 meters above the finished floor level."
}

# فهرسة الشروط (مرة واحدة عند بدء التشغيل)
condition_embeddings = {
    key: model.encode(text) for key, text in conditions.items()
}

def retrieve_condition(query, top_k=1):
    query_vec = model.encode(query)
    scores = {
        key: cosine_similarity([query_vec], [vec])[0][0]
        for key, vec in condition_embeddings.items()
    }
    ranked = sorted(scores.items(), key=lambda x: x[1], reverse=True)
    return ranked[:top_k]

# مثال استخدام
result = retrieve_condition("what is the minimum room area required?")
print(result)  # [('room_area', 0.87)]
```
هذا هو أساس الـ RAG pipeline بالكامل — بسيط ويوضح كل المفاهيم النظرية اللي شرحناها، وكافٍ تمامًا لحجم متطلبات التاسك.
